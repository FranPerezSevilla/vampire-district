# M1 — compiler-owned local lane topology contract

## Why this task exists

The production audit in PR #73 proved that the legacy `traffic-lanes.json.edges` collection cannot safely become lane/junction routing authority.

Those legacy edges are not one road segment between two physical junctions. `buildMacroAndLanes(...)` in `tools/city-compiler/district-streaming.js` builds each edge as a long district-anchor/portal route that may traverse multiple real road-network nodes. Runtime endpoint-to-nearest-junction inference therefore asks the wrong question.

M1 must correct the data contract before any vehicle consumes connector routing.

## M1.1 audit evidence

Validated on head `6e098646c93aebfe1db58585a11e2b85dfba173e`, GitHub Tests #2053 / run `32475274379` — full workflow green.

Production audit of the legacy manifest reported:

- 48 directed legacy lanes;
- 71 junction markers;
- 99 candidate connectors;
- 19 orphan directed lanes;
- 24 unmatched lane endpoints;
- 14 ambiguous endpoint/junction matches;
- 0 endpoint-position continuity failures;
- 96 tangent continuity failures;
- 71/99 candidates classified as U-turns;
- 0 duplicate connector IDs / lane-pair IDs.

This is not an activation-ready topology. The audit did its job by exposing the abstraction mismatch before visible traffic used it.

## Correct authority

The local traffic topology must be derived from `buildDistrictRoadNetwork(...)` output:

- each `network.segment` is one physical road segment between two explicit compiler node IDs;
- every physical segment produces exactly two directed lanes;
- lane ownership uses `fromNodeId` / `toNodeId`, never a nearest-junction radius heuristic;
- each directed lane is offset to the right-hand side of its travel direction;
- legal continuation candidates are outgoing directed lanes whose `fromNodeId` equals the incoming lane's `toNodeId`;
- immediate reversal on the same source segment is a U-turn and is non-preferred whenever another segment exists;
- degree-1 compiler nodes are explicit dead ends and may require an explicit reversal policy;
- degree-2 nodes remain explicit topology nodes even when they are only straight/corner/district-boundary continuation points;
- degree >= 3 nodes are physical junctions.

The legacy district-pair `traffic-lanes.json.edges` remain compatibility data until M8 migration. They are not deleted or repurposed during M1.

## M1.2 — compiler-owned directed lane graph

### Implementation

`tools/city-compiler/traffic-lane-topology.js` owns the pure compiler representation.

Required output:

- compiler node records;
- two directed lane records per `network.segment`;
- exact node ownership IDs;
- right-hand lane geometry;
- legal + preferred outgoing lane IDs;
- deterministic transition records;
- turn classification;
- explicit dead-end handling metadata;
- validation that rejects broken node ownership or wrong-side lane offsets.

### Safety rules

- No runtime driving activation.
- No geometric endpoint-to-junction guessing.
- No use of macro district centres as local coordinates.
- No hand editing of generated JSON.
- No deletion of legacy lane data yet.

### Exit gate

M1.2 is complete only when production compiler tests prove:

- directed lane count = `network.segments.length * 2`;
- every lane references existing compiler nodes;
- every lane is on the right side of travel;
- every transition shares the exact compiler node between incoming/outgoing lanes;
- preferred U-turns occur only where the compiler node has no alternative segment;
- output is deterministic/serializable;
- full CI is green;
- visible traffic remains unchanged.

## M1.3 — integrate compiler topology into the generated pack

After M1.2 is green, extend the streaming compiler schema additively. Do not replace legacy `edges` yet.

Recommended additive shape:

- `trafficLanes.localTopology` (or equivalent versioned field) contains the compiler-owned nodes/lanes/transitions;
- generated `traffic-lanes.json` is regenerated by compiler tooling, never hand edited;
- validation checks local topology against the same `network` used to build the pack;
- runtime diagnostics may load it read-only, but visible cars still use the existing movement authority.

## M1.4 — tangent-safe connector geometry on compiler lanes

Only after explicit node ownership exists should connector geometry be generated.

Connector hard gates:

- exact incoming lane end -> outgoing lane start endpoints;
- connector belongs to the shared compiler node;
- sampled geometry stays inside compiler-owned drivable/junction authority;
- first sampled heading follows incoming lane tangent within a strict tolerance;
- last sampled heading follows outgoing lane tangent within a strict tolerance;
- tangent failure is a rejection reason, never only a warning;
- no zero-length/pathological connector;
- no duplicate lane-pair connector;
- no arbitrary world-space steering.

The M0 quadratic-to-junction-centre connector is explicitly provisional and must not be activated. Prefer a tangent-preserving cubic/Hermite construction whose controls remain inside the allowed junction envelope.

## M1.5 — retire the legacy endpoint-inference topology path

Once compiler topology + connector safety are proven read-only:

- stop treating legacy district-pair edge endpoints as physical junction endpoints;
- remove/retire nearest-junction ownership inference from the activation path;
- retain only diagnostics necessary to explain/migrate legacy data;
- do not delete compatibility data needed by current traffic until M8.

## Gate before M2

Do **not** begin route-agent activation until all M1 gates are true:

1. compiler-owned local topology is generated and loaded read-only;
2. no local lane endpoint ownership is ambiguous because ownership is ID-based;
3. all activatable connectors are endpoint- and tangent-continuous;
4. all activatable connector geometry is inside drivable junction authority;
5. production compiler + unit + browser CI are green;
6. visible traffic behaviour remains unchanged.
